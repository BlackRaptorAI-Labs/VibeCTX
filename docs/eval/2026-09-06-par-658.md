# PAR-658 retrieval evaluation — legacy overlap ranker vs BM25

**Date:** 2026-09-06 · **Branch:** `build/par-658-bm25` · **Decision:** D-27, D-32
· **Re-run 2026-09-06 after the rework** — the D-23 stemmer's third step-1b repair
(the silent `e` put back: `noted` → `note`, `typing` → `type`), plus D-28 (computed
fence widths), D-29 (the snippet budget as a hard cap), D-30 (derived render fields
cleaned and clipped) and D-31 (each document split separately). Every number below
is from that re-run; the legacy baseline is frozen in the script and did not move.

**Nothing moved.** All 60 per-question rows are byte-identical to the previous run:
same top-1 for both rankers, same hits, same totals. The silent-`e` repair converges
`note`/`noted`/`noting`, `type`/`typed`/`typing`, `base`/`based`, `code`/`coded`,
`size`/`sized`, `page`/`paged` — and none of those words decides a question on this
corpus. D-28 to D-31 change how a response is rendered and how a multi-document
corpus is split; the eval ranks each library's primary document alone, so they
cannot move it. **No question flipped.**

## Verdict, first

**BM25 did not beat the legacy ranker on this probe set. Both score 18/60 top-1
hits (18/23 of the answerable questions). MEASURED, not asserted.** The two
rankers disagree on the top result for 14 of the 60 questions, but every one of
those 14 is a question this corpus cannot answer, so BM25 gained 0 hits and lost
0. PAR-658's "correct section in top result improves over the current ranker"
done-when is **NOT met on this corpus**; see *What this does and does not show*.

**Neither stemmer amendment flipped a question** — same 18 hits, same five
answerable misses, both times. The first (de-doubling and the silent-`e` cut)
changed the top-1 on two unanswerable questions (`prisma / relation include`,
`convex / schema define table`) and cost 16 tokens of average response; the
second (the silent `e` put back) changed nothing measurable at all. What both
fixed is real but invisible at top-1 here; the `zod / parse object schema` case
is dissected below.

## How the numbers were produced

- Script: `scripts/eval-retrieval.mjs`, run as `npm run build && node scripts/eval-retrieval.mjs`.
- D-32: the gold set is a versioned data contract (`schemaVersion: 1`) and the
  script validates its shape before it measures anything — the version, the `gold`
  array, every question's keys and types, every regex, and that `unanswerable`
  agrees with `expect.length === 0`. A mismatch throws and prints no numbers,
  because a half-read gold set produces numbers that look exactly like real ones.
  The `unanswerable` flag was kept rather than dropped: it records that the
  labeller judged the corpus unable to answer, which an empty array alone does not
  distinguish from an unfinished entry.
- Gold: `docs/eval/probe-gold.json` — 60 questions, being each of the 30 registry
  entries paired with each of its two `probeQueries`. Each question carries
  heading-path regexes for the section that would count as the correct top result,
  labelled by reading the fetched documents **before** either ranker was run over
  them, under the labelling rule stated in that file's header.
- Legacy baseline: the `tokenize` / `splitSections` / `rankSections` / `assemble`
  from `src/retrieval.ts` at 5b31f33, copied verbatim into the script so the
  baseline cannot drift with `src/`.
- Both rankers rank the **primary document only** — index links are not followed,
  so the two are compared on identical input.
- Response size is the rendered `assemble(ranked, 4000)` length divided by 4
  (VibeCTX's own approximate-token unit).

## Corpus provenance — read this before trusting the hit rates

Every one of the 30 documents in this run was the entry's
**`raw.githubusercontent.com` README fallback**. Not one docs-site
`llms-full.txt` / `llms.txt` primary was reachable from the build sandbox, which
has network access to `registry.npmjs.org`, `pypi.org` and
`raw.githubusercontent.com` only. The per-question table below records the
resolved URL class; the script prints each URL to stderr.

That matters enormously. A README is a fraction of an `llms-full.txt`: **37 of
the 60 probe queries have no correct answer anywhere in the document that was
fetched** (`expect: []` in the gold file, with a per-question reason). Prisma's
README never says "upsert"; the Stripe library README never says "checkout";
Tailwind's README is four sections of links. The probe queries were written
against the real docs sites, and the real docs sites are exactly what this
sandbox cannot see.

So these hit rates measure the two rankers **against a corpus neither was
designed for**. They are a valid A/B — same input, same gold — and an invalid
estimate of production quality in either direction.

## What this does and does not show

**Even.** Neither ranker wins a single question the other loses. On the 23
answerable questions both pick the same section 18 times, and both miss the same
five: `ai-sdk / streamText tool calling`, `zod / parse object schema`,
`bun / Bun.serve http server`, `playwright / locator click`,
`astro / islands client directive`.

**BM25 answers more often (12 → 7 "no sections matched").** The new tokenizer's
camelCase splitting is what does most of it: `useUser hook` tokenizes to
`use, user, useuser, hook`, and `use` occurs in almost any document, so clerk's
README now returns a section where the legacy ranker correctly returned nothing.
The amended stemmer adds one more, and it is a fair illustration of the trade:
`convex / schema define table` now tokenizes to `schema, defin, tabl`, and
`defin` matches `user-defined` in "Repository layout" — a real morphological
match to a section that still does not answer the question. Recall up, precision unchanged
**on this corpus** — and on a README the extra recall is noise. On an
`llms-full.txt`, where the answer usually does exist, the same behaviour is the
point of the change; that is a hypothesis this run cannot test.

**Responses got 13% longer (861 → 976 tokens).** Same cause: BM25 admits more
sections above zero, and `assemble` fills the 4,000-token budget with them. The
first stemmer amendment accounts for 16 of those 115 tokens; the second accounts
for none.

**Both stemmer defects are fixed, and neither flipped the question it was blamed
for.** Before the first amendment, `tokenize("parse")` → `["parse"]` while
`tokenize("parsing")` → `["pars"]`: `ing` came off without the silent `e`, so the
two never met. They now both stem to `pars`, together with `parsed` and `parses`
(MEASURED — `test/tokenize.test.ts` "stems inflections of the same word to one
token", eleven families). The second defect was the mirror image, and worse for
being invisible: `noted` → `not`, `seed` → `see`, `typed`/`typing` → `typ`
against `type` → `type`. Cutting a suffix off a silent-`e` verb left a bare
three-letter stem while the base form kept its `e`, so the pair never met AND two
of the stems — `not`, `see` — were high-frequency words that a document full of
ordinary English matches constantly. Repair (d) converges them on the base form
(MEASURED — "(d) converges the review gate's silent-e probe list", nine families).

**`zod / parse object schema` still misses, and the earlier note overstated the
stemmer's part in it.** MEASURED on the same cached document, top-1 before → after
the amendment: "What is Zod?" 2.527 → 2.678 stays first; the gold section
"Basic usage > Parsing data" gains from the repair, 1.986 → 2.143, but was third
before and is third now, behind "Basic usage > Handling errors" (2.273 → 2.329)
and "Basic usage > AOT compilation" (2.271 → 2.271). Term counts for the three
query terms `pars, object, schema`, MEASURED over the same tokenizer: the gold
section carries 5 / 0 / 4 in 79 tokens; "Handling errors" 7 / 1 / 3 in 182;
"AOT compilation" 2 / 3 / 11 in 194; and the winner "What is Zod?" 3 / 1 / 1 in
54. Each rival beats the gold section on a term it lacks or barely has, and the
short intro wins on density — a top-1 ordering problem, not a tokenizer problem.
The remaining five answerable misses are unchanged.

**Three non-convergences are deliberate and documented in `src/tokenize.ts`,**
each pinned by a test: `using` (a stopword; alone, `ing` → `us` is under the
three-character floor), `handler` (no agent-noun rule — an `er` rule would also
merge `router` into `route`), and `embed` → `emb` against `embedded` → `embed`
(the `ed` in `embed` is not a suffix, and `emb` is not consonant-vowel-consonant,
so the silent-`e` repair cannot reach it). Three over-stems are tolerated for the
same reason: `seed` → `see` (the `d`-cut that carries `used` → `use` cannot avoid
it — both are C-V-V-`d`), `stripe` → `strip` and `middleware` → `middlewar`.
Queries and documents run through the same function, so those cost precision,
never a match.

**Why the silent-`e` repair is narrow.** The rework brief proposed raising the
`ing`/`ed` cut floor to four characters. MEASURED against a scratch implementation
of exactly that: it gives `added` → `adde` (the `d`-only fallback then fires),
breaking the pinned `added` → `add`, and it leaves `noting` and `typing`
unstemmed, so half the probe list still does not converge. Porter step 1b's
`*o` add-`e` rule, restricted to a three-letter CVC stem, converges the whole
probe list, leaves `added` alone, and leaves `string` → `str` alone (three
consonants, so no `e` is invented for it).

**`mode: "snippets"` has something to return on 35 of the 60 questions** — that is
a capability count on this corpus, not a quality measurement. No gold set exists
for snippets yet.

## Reproducing

```
npm run build
node scripts/eval-retrieval.mjs
```

The script caches fetched documents under `$TMPDIR/vibectx-eval-cache` (override
with `DOCS_CACHE_DIR`), so a second run is offline and byte-identical. Run it
from a machine with unrestricted network access to get the numbers that matter:
the same 60 questions against the `llms-full.txt` primaries. Those numbers do not
exist yet and are not claimed here.

## Standards applied

No published standard governs retrieval evaluation for this use. The practice
applied is a fixed, pre-labelled top-1 relevance set with a frozen baseline
implementation, scored by exact A/B on identical input — the gold set was written
from the documents before either ranker was run and was not adjusted afterward.
