# PAR-827 retrieval evaluation — re-labelled against the real, current corpus

**Date:** 2026-09-20 · **Phase:** 8 (Retrieval honesty and coverage) · **Decision:** D-9x
(Phase 8 entry, `docs/decisions.md`) · **Supersedes:**
[`2026-09-06-par-658.md`](2026-09-06-par-658.md) as the CURRENT measurement — that file is kept,
unedited, as the historical record of what the 2026-09-06 run actually measured (a
GitHub-README-only corpus, forced by a network-less sandbox); it is not wrong for what it says,
it describes a corpus this pipeline no longer serves for 25 of the 30 libraries.

## What changed and why this run exists

The 2026-09-06 run's own text says it plainly: "The docs-site `llms-full.txt` primaries these
libraries publish — the documents the ranker is meant for — are unreachable from that sandbox, so
this is not yet a measurement of the ranking on real documentation." This environment has live
network access. This run is that measurement.

All 60 questions in `docs/eval/probe-gold.json` were re-labelled from scratch: each library's
primary document was fetched live through the real `getLibraryDoc` fetcher (the same path
`get_docs` and `scripts/eval-retrieval.mjs` both use), read, and a human judgement call made
about whether any section of it would materially help a developer asking that question — never
by checking what either ranker returned first (D-27's rule). `docs/eval/probe-gold.json` moved to
`schemaVersion: 2`: it now also records, per library, the EXACT url and a `corpusKind` label
(`docs-site-full-text`, `index-only`, `github-readme-fallback`, `docs-repo-page-fallback`) the
labels were verified against, and `scripts/eval-retrieval.mjs` refuses to print a score at all
when a run's actually-resolved URL disagrees with the recorded one — the exact class of drift
this re-labelling pass itself was needed to close, now structurally prevented from recurring
silently.

## Verdict, first

**33 of 60 questions are answerable at all under the current corpus. BM25 and the legacy ranker
tie: 11/60 top-1 hits each (18.3%), 11/33 of the answerable questions (33.3%). MEASURED, not
asserted** — see the full per-question table below, produced by
`node scripts/eval-retrieval.mjs` against a fresh cache, 2026-09-20.

This is LOWER than the 2026-09-06 run's 18/60 (30%) / 18/23 of answerable (78%). That is the
expected, honest result of measuring against the real corpus rather than a thinner stand-in, not
a regression in the ranker: **the real corpus is structurally harder to rank against than the
README fallback was**, for two independent reasons, both MEASURED here for the first time:

1. **This eval script does not follow index links** (D-27's original design, unchanged by this
   item): it ranks only the primary document `getLibraryDoc` returns. 11 of the 30 libraries'
   real, live primary document is itself an index of links with no prose body at all — next.js,
   react, supabase, shadcn, stripe, ai-sdk, expo (its `llms-full.txt` is, despite the name, 69%
   link lines), clerk, anthropic-sdk, tanstack-query, motion. For these, most questions are
   honestly `expect: []` here even where `get_docs` (which DOES follow links — see PAR-844/PAR-845
   for that separate mechanism and its own, different measurement) could plausibly find more.
2. **4 of the 30 libraries no longer resolve to what their registry `urls` list first** at all,
   live: tailwindcss and firebase fall back to a raw GitHub README (their `llms-full.txt`/
   `llms.txt` now 404); react-router and astro resolve to one specific docs-repo page rather than
   an index or a full dump. None of these were changed in this item (PAR-839 investigates
   tailwindcss's case specifically).

Of the 18 real, full-text corpora (drizzle-orm, prisma, trpc, zod, hono, bun, vite, convex,
openai, vitest, sveltekit, nuxt, vue, resend, plus playwright/react-router/astro/firebase's
smaller real pages), several MASSIVELY larger than the README fallback ever was (prisma 6.0M
chars, openai 4.76M, nuxt 4.79M, drizzle-orm 3.67M) — ranking precisely inside a multi-megabyte
document with many structurally similar sections (per-dialect or per-framework repeats of the
same heading, e.g. drizzle-orm's `### Filters` appears once per SQL dialect) is a genuinely
harder top-1 problem than a short README ever posed, and several of this run's misses are BM25
and the legacy ranker both landing on a plausible but different section of a very large,
repetitive document, not a wrong or absent answer in the corpus.

## What this does and does not show

**Does show:** a real, live, honest floor for what this ranker achieves against the actual
documents this tool serves today — not a proxy corpus. Every one of the 33 answerable questions
has a real, verified, quoted piece of evidence in `docs/eval/probe-gold.json`'s own `note` field
(a real code example or explanation actually present in the fetched document, with the exact
heading it lives under).

**Does not show:** a verdict on BM25 vs. the legacy ranker specifically — they tied on this run,
same as the 2026-09-06 run, for the same reason that run named (the ranker choice is not what a
thin/index-only corpus or a many-times-repeated heading shape is limited by). It also does not
mean retrieval is "bad" in an actionable sense on its own: 11 of these misses are the ranker
choosing a different, real, on-topic section of a large document over the specific one this
labelling pass judged best — a precision question, not an availability one, and precision was
explicitly out of scope for this measurement pass (see PAR-844's own docs/decisions.md entry on why
`doctor`'s health check does not grade precision either).
